Run:ai with NVIDIA and AMD GPUs

How to plan one open-source NVIDIA Run:ai 3.0 cluster that schedules an NVIDIA and an AMD GPU on the same server: the AMD GPU Operator next to the NVIDIA GPU Operator, what Run:ai counts for AMD, per-vendor quotas, and dashboards that show both vendors on the same panels. From a real lab build.

Author Manmohan Brahma Run:ai 3.0.20, open source AMD GPU Operator 1.5.1 GPUs RTX A6000 + Radeon PRO W7900 Installation Guide oif on GitHub All guides
Lab build. Open-source Run:ai is community software without NVIDIA support, and it documents NVIDIA GPUs. The AMD GPU is scheduled through the standard Kubernetes device plugin; the limits observed are listed in this guide. Both GPUs are workstation cards.

1What this guide covers

This guide extends the single-node Run:ai deployment from the Single-Node Run:ai Deployment Guide with an AMD GPU, so that one open-source Run:ai 3.0 cluster schedules NVIDIA and AMD GPUs on the same server: the AMD GPU Operator next to the NVIDIA GPU Operator, Run:ai quotas on both vendors, per-vendor caps, and one set of dashboards for both.

It is the planning half of a pair. The companion Installation Guide has every command and its output.

It is a step of a larger project: one open-source platform that schedules, serves, benchmarks and observes LLMs on NVIDIA and AMD GPUs, so the two can be compared on equal terms.

2Architecture

Additions to the single-node Run:ai deployment:

  • AMD GPU Operator (namespace kube-amd-gpu): controller, device plugin (amd.com/gpu), node labeller (amd.com/gpu.* labels) and device metrics exporter (port 5000, Prometheus ServiceMonitor). It uses the kernel's own amdgpu driver; it builds and loads nothing.
  • Shared Node Feature Discovery: the instance from the NVIDIA GPU Operator also runs AMD's detection rule, which labels the node feature.node.kubernetes.io/amd-gpu=true.
  • Run:ai unchanged: the KAI Scheduler places pods asking for amd.com/gpu exactly like pods asking for nvidia.com/gpu, and counts them against the same project quota.
  • Per-vendor caps: a Kubernetes ResourceQuota per Run:ai project namespace.
  • Observability: recording rules map the DCGM exporter and the AMD exporter onto one oif:* schema; two Grafana dashboards read only that schema; Grafana is published on the Run:ai domain.

The two vendors share the node without interfering: each operator's device plugin advertises its own resource name, the NVIDIA container runtime is used only by pods that ask for it (runtimeClassName: nvidia), and AMD pods get /dev/kfd and the GPU's render device from the AMD device plugin.

Still open: the node's GPU memory and free-device figure come from the NVIDIA GPU only, and the scheduler adds both vendors into one GPU count per node, so on a node with both it can place an NVIDIA workload while only the AMD GPU is free (the kubelet then rejects the pod). With one vendor per node, as in production clusters, this does not arise.

6Per-vendor quotas

Run:ai separates GPU types with node pools, and a node pool is selected by one node label: a node belongs to exactly one pool. With both GPUs in one node, separate nvidia and amd pools are impossible, and a KAI queue has a single gpu quota for every vendor.

OptionVerdict
Kubernetes ResourceQuota per vendor in each project namespace, Run:ai keeps the totalchosen: native, small, removed with the cluster
A second Kubernetes node in a virtual machine with the AMD GPU passed through, then one node pool per vendorrejected for one host: a much larger host change, and Run:ai's inventory would still not list the AMD GPU
Accept one shared quotarejected: a project could not be limited per vendor

Semantics to know:

LimitEnforced byA pod over it
Project totalRun:ai schedulerwaits in the queue
Per vendorKubernetes ResourceQuota oif-gpu-vendoris refused when created (exceeded quota)

There is no borrowing per vendor between projects. On a cluster with one vendor per node, real Run:ai node pools replace the ResourceQuota.

11Checklists

Before installing

  • The single-node Run:ai deployment is installed and its quota test passed
  • The AMD GPU is on the amdgpu driver and /dev/kfd exists (./oif check)
  • Display-only AMD cards are listed in ISOLATE_GPUS
  • Outbound HTTPS to docker.io and rocm.github.io

After installing

  • kubectl -n kube-amd-gpu get pods shows four pods Running
  • The node offers amd.com/gpu and nvidia.com/gpu
  • A pod in a Run:ai project gets the AMD GPU; a project without quota waits
  • A project with per-vendor caps refuses a pod over its cap
  • OIF Fleet shows both GPUs on every panel
  • OIF Scheduling shows GPUs in use and waiting per vendor
