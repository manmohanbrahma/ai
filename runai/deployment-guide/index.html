Single-Node Run:ai Deployment

How to plan open-source NVIDIA Run:ai 3.0 on one GPU server: the control plane and the cluster on a single-node Kubernetes cluster, with the NVIDIA GPU Operator, Prometheus, an ingress controller, a domain without a DNS server, and TLS from a private CA. Architecture, tested versions, sizing, network, security and operations, from a real lab build.

Author Manmohan Brahma Run:ai 3.0.20, open source Kubernetes 1.35.9, single node GPU NVIDIA RTX A6000 Installation Guide oif on GitHub All guides
Lab build. Open-source Run:ai is community software without NVIDIA support. Run:ai documents data-centre GPUs; the workstation GPU used here schedules as a whole GPU, but GPU fractions need driver r615 or later.

1What this guide covers

NVIDIA open-sourced the complete Run:ai platform on 13 October 2026: the control plane (UI, REST API, identity, organisation, policies, metrics), the cluster services, the KAI Scheduler with projects, quotas and node pools, and the installer, under Apache-2.0. This guide describes how to deploy open-source Run:ai 3.0 on one GPU server: control plane and cluster on the same single-node, upstream Kubernetes cluster, with the NVIDIA GPU Operator, Prometheus, an ingress controller, a domain and TLS, all installed and removed by one command line, oif (Open Inference Fabric).

It is the planning half of a pair. The companion Installation Guide has every command and its output.

The build is the first step of a larger project: one open-source platform that schedules, serves, benchmarks and observes LLMs on GPU servers.

2Architecture

Everything runs on one host:

  • Kubernetes 1.35 (kubeadm), single node; the control plane also runs workloads.
  • Run:ai control plane (namespace runai-backend): UI, REST API, Keycloak, PostgreSQL, NATS, Thanos, Traefik and about 20 services.
  • Run:ai cluster (namespace runai): the KAI Scheduler (runai-scheduler), queue, pod-group and node-pool controllers, admission webhooks, a Prometheus instance, and the agent that syncs with the control plane.
  • GPU enablement: NVIDIA driver on the host from the Ubuntu archive, NVIDIA GPU Operator for the container toolkit, device plugin, feature discovery and DCGM metrics.
  • Entry point: one MetalLB address on the HAProxy ingress controller; the Run:ai domain and its wildcard resolve to it.

Requests from a browser or an API client reach HAProxy on the load-balancer address over HTTPS; HAProxy routes by host name to Run:ai's Traefik, which fronts the control plane. The Run:ai cluster services talk to the control plane through the same domain. GPU workloads submitted through Run:ai projects are placed by the KAI Scheduler on the GPU through the NVIDIA runtime.

sslip.io. Run:ai needs a fully qualified domain and a wildcard below it. Without a DNS server of your own, sslip.io answers any name that contains an IP address with that address: runai.192-0-2-240.sslip.io resolves to 192.0.2.240, and so does anything.runai.192-0-2-240.sslip.io. To use your own domain instead, set RUNAI_DOMAIN before installing and create runai.example.com and *.runai.example.com records pointing to the first MetalLB address.

Cluster DNS answers the Run:ai domain itself. The Run:ai cluster services reach the control plane through its domain. oif adds a block to CoreDNS that answers the domain and every name below it with the ingress address, so pods do not depend on external DNS for it. This was found necessary on the reference host, where one of the two DNS servers in the host's settings refuses every query: the host's resolver falls back to the other one, but CoreDNS does not, and pods saw random lookup failures (see Known issues).

Access from a laptop. MetalLB announces its addresses on the host's network segment. A client that reaches the host only through a VPN that routes the host's own address cannot reach the load-balancer address directly; an SSH SOCKS tunnel to the host, with a browser using it and resolving names remotely, works (Installation Guide, Open the Run:ai UI).

6TLS and certificates

oif creates a private certificate authority on the host and one server certificate:

ItemDetail
CARSA 4096, 10 years, CN=oif local CA <host>; key in /var/lib/oif/pki (root only, mode 600)
Server certificateRSA 2048, 825 days; SANs: the domain, *.domain, *.inference.domain
Given to Run:aias tls.certPath, tls.keyPath and tls.caChainPath in the installer's configuration
Given to usersthe CA's public certificate, ~/oif-ca.crt, to import once into a browser or OS trust store

The CA is kept when the install is run again, so browsers that trust it keep trusting it. To use certificates from your own CA, the same three installer fields take them.

Run:ai recommends shared storage (NFS) for training data so that workloads read the same files on any node. A single-node cluster does not need it; local-path volumes are enough for the control plane and for inference workloads.

8Security

  • Secrets. Passwords and tokens are read from .env or asked at the prompt with the input hidden, saved only in /var/lib/oif/settings.conf (mode 600) and as Kubernetes Secrets. Grafana's admin password is passed to Kubernetes from a file, never as a command-line argument.
  • No join credentials left. kubeadm init prints a bootstrap token and a certificate key; oif keeps that output in the root-only state folder, deletes the join tokens and the uploaded-certificates secret (a single node needs neither), and redacts tokens and keys from the readable log.
  • Run:ai administrator. Run:ai generates the first administrator's password and stores it in the secret runai-backend-gen-tenants-manager; only root can read it. Change it after the first login.
  • Supply chain. Every image and chart is pinned; Helm, the runai-installer binary and every upstream manifest are checked against SHA-256 checksums. Open-source Run:ai images and charts come from NGC without credentials.
  • Exposure. The UI and API are reachable only on the load-balancer address on the host's subnet. Nothing is published outside the lab network.

12Checklists

Before installing

  • Ubuntu 22.04, 24.04 or 26.04 server, 16+ CPU threads, 64 GB+ memory, 150 GB+ free under /var/lib
  • A data disk for images and volumes (200 GB or more)
  • An NVIDIA GPU, Ampere or newer
  • 2 to 5 free addresses on the host's subnet for MetalLB
  • Outbound HTTPS to registry.k8s.io, nvcr.io, ghcr.io, quay.io, docker.io, github.com, helm.ngc.nvidia.com and the Ubuntu archive
  • Every DNS server in the host's settings answers (./oif check tells)
  • A user with sudo; one reboot is acceptable

After installing

  • kubectl get nodes shows the node Ready
  • kubectl get pods -A shows every pod Running or Completed
  • The node advertises nvidia.com/gpu
  • https://runai.<lb-ip>.sslip.io opens without a certificate warning after importing the CA
  • The cluster shows Connected in Run:ai
  • A project with a GPU quota runs a GPU workload, and a project without quota waits
