Deploying Nutanix Enterprise AI on Red Hat OpenShift

How to run Nutanix Enterprise AI 2.8 on Red Hat OpenShift, for inference on x86_64 CPU nodes and on NVIDIA GPU nodes: what OpenShift needs that a Nutanix Kubernetes Platform cluster provides out of the box, the deployment steps, and what we learned doing it.

Author Manmohan Brahma NAI 2.8.1, air-gapped bundle OpenShift 4.22.17, single node Accelerators x86_64 CPU · NVIDIA GPU Lab GPU NVIDIA RTX A6000
Check the support matrix first. NAI supports CNCF-conformant Kubernetes distributions listed in its requirements. Confirm that your OpenShift version is listed for your NAI release. The lab in this paper used OpenShift 4.22, whose managed Gateway API version differs from what NAI 2.8.1 needs; section 4 explains the override the lab used, which Red Hat does not support.

1Why NAI on OpenShift

Many enterprises standardise on Red Hat OpenShift for their container platform. Nutanix Enterprise AI (NAI) adds a governed model-serving service on top: a catalog of validated models, guided endpoint creation, one secure OpenAI-compatible gateway, role-based access, per-endpoint API keys, audit logging and per-endpoint metrics. NAI serves models with vLLM and runs as ordinary Kubernetes workloads, so it can run where the customer's platform team already operates.

The same NAI release serves two kinds of hardware:

  • x86_64 CPU nodes for small models, development, and sites without accelerators. NAI uses its CPU build of vLLM.
  • NVIDIA GPU nodes for production throughput and larger models. NAI uses its GPU build of vLLM, and the NVIDIA GPU Operator provides the driver and device plugin.

5Deployment steps

  1. Install OpenShift

    Any supported installation method works. For a single node, the agent-based installer builds a bootable ISO from install-config.yaml and agent-config.yaml:

    openshift-install agent create image --dir install/
# boot the server (or VM) from install/agent.x86_64.iso, then
openshift-install agent wait-for install-complete --dir install/
  2. Install the platform operators

    From OperatorHub: Node Feature Discovery, LVM Storage (with an LVMCluster on a spare disk), cert-manager Operator for Red Hat OpenShift and CloudNativePG. For GPU nodes add the NVIDIA GPU Operator and create its ClusterPolicy. Wait until the node reports the GPU:

    oc get node -o jsonpath='{.items[0].status.allocatable.nvidia\.com/gpu}'
  3. Load NAI's images into a registry

    Push every image from the NAI air-gapped bundle to a registry the cluster can reach, keeping the names, then mirror docker.io to it:

    skopeo copy oci:nai-oci:@<n> docker://registry.example:5000/nutanix/<image>
oc apply -f image-tag-mirror-set.yaml -f image-digest-mirror-set.yaml
  4. Prepare OpenShift for NAI

    Grant the security policies, create the RWX storage class, and make sure the Gateway API version matches NAI's:

    oc adm policy add-scc-to-group privileged system:serviceaccounts:nai-system
for ns in nai-system nai-admin envoy-gateway-system kserve lws-system opentelemetry-operator-system; do
  oc adm policy add-scc-to-group anyuid system:serviceaccounts:$ns
done

    Do not create the nai-admin namespace yourself: the nai-core chart creates it and refuses a namespace that already exists.

  5. Install the NAI components in order

    With Helm, from the NAI chart bundle, each pointed at the NAI images: Envoy Gateway CRDs and Envoy Gateway (with the AI Gateway extension), KServe CRDs, LeaderWorkerSet, the OpenTelemetry operator, NAI operators, KServe in RawDeployment mode, and finally nai-core with the RWO and RWX storage classes and the global rate limit disabled.

  6. Expose NAI

    Create a Route to the NAI gateway service. Use the service's actual HTTPS port name (https-443 in NAI 2.8.1):

    oc create route passthrough nai --service=<nai-gateway-svc> --port=https-443 \
  --hostname=nai.apps.<cluster>.<domain> -n envoy-gateway-system
  7. Log in and create endpoints

    Open https://nai.apps.<cluster>.<domain>/nai, sign in as admin with the initial password from the nai-default-user secret, change it, and apply the NAI licence. Then import a model and create an endpoint: choose CPU for x86_64 inference or GPU Passthrough for an NVIDIA GPU.

The lab automated all of these steps in one interactive script, which builds single-node OpenShift on a VM or bare metal, installs the operators, loads the NAI bundle and deploys NAI. It resumes after reboots and asks before any unsupported change.

8Lessons learned

  • Grant anyuid, not a broad non-root policy. A cluster-wide nonroot-v2 grant made OpenShift force "must not run as root" onto NAI's ClickHouse, which then failed; restricted-v2 gave the IAM UI a random user that could not write its cache. Restart pods after changing grants.
  • Let the charts own their namespaces. Pre-creating nai-admin stops nai-core from installing.
  • Plan the Gateway API version. On OpenShift 4.19 and later the ingress operator owns the Gateway API CRDs. Pick an OpenShift release that matches NAI's requirement wherever possible.
  • Secure Boot and the NVIDIA driver. The GPU Operator compiles its driver inside the cluster; Secure Boot rejects that unsigned module. Use NVIDIA's precompiled signed driver where available, or disable Secure Boot on the node.
  • GPU passthrough for VM-based clusters. Reserve the GPU for passthrough at host boot rather than releasing it from a running driver, and keep the VM's memory on the GPU's NUMA node.
  • Size the node for NAI's own reservations. At 32 vCPU the first CPU endpoint stayed Pending ("Insufficient cpu"): NAI's platform pods already reserved about 19 cores. Resizing to 48 vCPU let it schedule. Endpoint memory must also meet the model's minimum, or NAI rejects the request (NAI-10014).
  • Same model, very different speed. On this lab the GPU endpoint generated about 228 tokens/s against about 0.8 on 8 CPU cores for a 1B model. CPU endpoints suit light use; tune them before relying on them.
  • No load balancer is needed. NAI's gateway reports no external address without one, which is expected; the Route provides access.

9Next steps

  • Tune CPU inference (thread pinning, CPU-engine settings, Intel AMX on supported CPUs) and measure CPU and GPU endpoints under load through NAI's gateway.
  • Test larger models: an 8B-class model on the GPU, and the CPU sizing it needs.
  • Repeat on an OpenShift release whose managed Gateway API matches NAI's requirement, to remove the override.
  • Extend to multi-node OpenShift with dedicated GPU worker nodes.
