Deploying Nutanix Enterprise AI on Nutanix Kubernetes Platform

How to plan a single-node Nutanix Enterprise AI (NAI) 2.8.1 deployment on Nutanix Kubernetes Platform (NKP) 2.18 that serves models on both an NVIDIA and an AMD GPU: architecture, tested versions, sizing, network, storage, models and day-2 operations, from a real lab build.

Author Manmohan Brahma NAI 2.8.1, air-gapped bundle NKP 2.18.0, single node GPUs NVIDIA RTX A6000 · AMD Radeon PRO W7900 Installation Guide All guides
Two stacks. The Stock stack is unmodified NAI on NVIDIA. The Moded stack adds AMD GPU support through lab patches that Nutanix has not validated; use it for evaluation, not where Nutanix support is required.

1Architecture

One server runs everything: a single-node NKP cluster, NAI on top of it, a local image registry and model storage. Requests enter through a load-balancer address, and NAI starts one engine pod per endpoint on one whole GPU.

The installer offers two stacks. Choose Stock unless you need AMD GPUs.

Stock stackModed stack

3Hardware and sizing

The platform itself reserves about 34 CPUs and 50 GiB of RAM before any model runs; everything else on the host is available to endpoints. Size the host for the largest models you plan to serve at the same time, one whole GPU per endpoint.

A third, low-end AMD card in the reference host (Radeon PRO W6400) is bound to vfio-pci at boot so neither the driver nor Kubernetes uses it. Do the same for any GPU that should not serve models.

Sizing rules

  • GPU memory: the model's weights plus its KV cache must fit on one GPU; NAI assigns whole GPUs, never a share. A 48 GB card serves models up to roughly 20–30B parameters at 8-bit or 4-bit precision, or smaller models at 16-bit.
  • Endpoint pods: start at 8 CPUs and 16–24 GiB of RAM for small models on a GPU; NAI's endpoint form sets both.
  • Boot disk: keep at least 150 GB free. Engine images are pulled onto it, and running out triggers kubelet DiskPressure, which evicts pods across the cluster.
  • Data disk: plan for every model at least twice — the source copy you import from and NAI's own copy in its model volume — plus about 100 GB for the registry.
  • Measured on the reference host: Llama-3.2-1B-Instruct (NAI catalog) on the W7900 answered with a 0.33 s first token at 184 tokens/s for one user. Throughput comparisons of the two GPUs under load are in the GPU benchmark hub.

The installer warns, but continues, below these minimums: 32 CPU threads, 128 GB of RAM, 600 GB free for the installation folder (900 GB for the Moded stack), 200 GB for the model folder and 200 GB under /var/lib for container images.

Plan one host address, a small load-balancer pool on the same subnet, and a DNS name for the NAI gateway whose certificate your clients trust.

Gateway certificate. The installer turns on NAI's built-in cert-manager option, which gives the gateway a self-signed certificate for nai.<cluster-name>.lab (secret nai-system/ingress-certificate), valid for 90 days and renewed automatically. Browsers show a warning, and clients must skip verification or trust it explicitly. Each renewal produces a new self-signed certificate, so anything that trusts the old one must be updated.

DNS. That name is not registered anywhere by default, so users connect by IP. Two features need the name to resolve and the certificate to be trusted:

  • the Remote NAI provider in the Agentic Gateway, whose Hostname field accepts only a DNS name and verifies the certificate;
  • any client that verifies TLS properly.

Recommendation for production. Create a DNS record for the gateway (for example nai.example.com → the second pool address) and replace the self-signed certificate with one from your corporate CA for that name. In a lab, a CoreDNS hosts entry plus trusting the self-signed certificate inside nai-api achieves the same; the Installation Guide has the commands.

Remote access. If users reach the host over a VPN that routes only the host's own address, the load-balancer addresses are unreachable from their laptops. Use an SSH SOCKS tunnel through the host, as described under Client access.

5Storage

Put all persistent data on one large data disk: local volumes for platform databases, and an NFS share on the same host for models. Three storage classes result.

Storage classTypeBacking (reference)Used by
localvolumeprovisioner (default)Local PVs, ReadWriteOnce20 directories bind-mounted at /mnt/disks/vol01–20NKP and Kommander: Prometheus, Grafana, OpenCost, Git operator
nai-localLocal PVs, ReadWriteOnce8 directories at /mnt/nai-disks/vol1–8NAI: PostgreSQL (nai-db), ClickHouse and its keeper, Valkey, NAI Labs data
nai-nfs-storageNFS (csi-driver-nfs), ReadWriteManyHost export of the model folder (/shared_storage/nai-models)One volume per imported model

How model storage works. When you import a model, NAI creates a ReadWriteMany volume on nai-nfs-storage and copies the model into it: a catalog model is downloaded from Hugging Face or NGC, and an NFS model is copied from a path you give, such as /shared_storage/nai-models/import/<model>. Every endpoint pod mounts that volume read-only at /mnt/models. The copy runs at about 25–30 GB per minute on the reference NVMe disk.

Capacity planning

  • Models: their size on disk twice (the import source and NAI's copy), plus headroom for the versions you keep.
  • Platform databases on nai-local: tens of GB; logs and metrics in ClickHouse grow with traffic.
  • Local volumes report the size of the whole disk because they are directories, not partitions. Watch the disk's real usage instead (df -h /shared_storage).
  • The NFS export must allow the host address and the pod network (192.168.0.0/16 in the reference); endpoint pods mount it through the host.

For a multi-node cluster, replace both local classes with real shared storage, for example Nutanix Files or another ReadWriteMany NFS service, and a block CSI driver for ReadWriteOnce volumes.

6Air-gapped images

NKP and NAI are installed from Nutanix's air-gapped bundles, served to the cluster by a registry on the host itself. The host still needs limited internet access during installation.

Bundles to download from the Nutanix portal (portal links expire after about an hour; the installer accepts a link or a local file):

BundleFile nameSize
NKP air-gapped bundlenkp-air-gapped-bundle_v2.18.0_linux_amd64.tar.gz29.3 GB
NAI image bundlenai-v2.8.1.tar70.1 GB
NAI Helm chartsnai-helm-charts-2.8.1.tarunder 0.1 GB

Local registry. The installer runs registry:2 as the systemd service nkp-registry on port 5000 of the host (plain HTTP, no authentication, data under the installation folder). It pushes the NKP, Kommander and catalog images and every image in the NAI bundle into it (106 GB on the reference host, Moded stack). The cluster is created with this registry as its mirror for all image pulls, so endpoints pull engine images from the host, not the internet.

Internet access still used during installation

  • Ubuntu package archive, for host packages missing from the offline repository.
  • Docker Hub: registry:2, the NFS CSI driver images, the KServe storage initializer and, for the Moded stack, the AMD GPU Operator and ROCm vLLM base images (about 75 GB).
  • GitHub and rocm.github.io: the NFS CSI and AMD operator Helm charts.
  • Ubuntu 26.04 only: building NKP's OS package bundle.

Catalog models are downloaded later, at import time, from Hugging Face or NGC unless you import them from NFS. The registry has no authentication: keep port 5000 reachable only from the host and cluster networks.

7Models and endpoints

A model is imported once and stored by NAI; an endpoint serves it on one GPU (or on CPUs) with an engine NAI picks from the GPU type. Applications reach an endpoint with an API key that must be linked to that endpoint.

Two kinds of model

SourceNAI catalog: Hugging Face or NGC, needs a hub tokenAny Hugging Face-format folder on NFS, or a hub repo

Engine per GPU type

amd-gpu-passthroughAMD (reference: Radeon PRO W7900)rocm/nai-vllm-rocm:v0.29.0-rocm10.1.0, Moded stack only

Rules to plan around

  • Capabilities choose the engine. Tick only what the model really does when importing a custom model: ticking text-to-image makes NAI start its image-generation server instead of vLLM. For a chat model tick only text-to-text, plus tool calling if it supports it.
  • One endpoint, one whole GPU. With two GPUs, at most two GPU endpoints run at a time; a new one waits until a GPU is free.
  • API keys are linked to endpoints by name at the time you link them. Deleting and re-creating an endpoint, even with the same name, drops those links; re-link the keys afterwards.
  • Endpoint resources (CPU, memory) are Kubernetes requests and limits on the engine pod. Leave a margin: the pod is killed if it exceeds its memory limit while loading a model.
  • Readiness is a TCP check on port 8000. An endpoint shows Ready once the engine listens, which can be before a slow model has finished loading.

Bring your own engine (custom models). A custom engine image is selected per endpoint (engine vllm, source custom, image name and tag). NAI starts it as vllm serve /mnt/models --served-model-name <endpoint> …, so the image must accept that command and serve the OpenAI API on port 8000. It runs as user 65534 with a read-only root filesystem, all capabilities dropped and only /tmp, /dev/shm and the home directory writable; point every cache at /tmp.

NAI 2.8.1 adds ready-made applications (NAI Labs) and an Agentic Gateway on top of the endpoints. Agent is on after installation; Chat and Talk to My Data must be switched on with one Helm value.

Plan for these limits

  • Labs Chat checks an endpoint with a short test request that must answer within 5 seconds, and allows 60 seconds between streamed tokens. Very large or slow models fail that check; use a model that answers in a few seconds.
  • The NAI gateway ends inference requests after 300 seconds (route nai-dataplane-httproute). Long generations need streaming, or a higher timeout.
  • Talk to My Data stores documents in a 20 GiB volume on nai-local with the built-in ChromaDB. For larger collections, point it at an external Milvus.
  • A Remote NAI provider pointing at this same NAI is only useful for demonstrations; it is meant for reaching a different NAI cluster.

9Client access

Applications use NAI like the OpenAI API: base URL https://<nai-ip>/enterpriseai/v1, an NAI API key as the Bearer token, and the endpoint name as the model. Any OpenAI-compatible SDK or tool works unchanged.

WhoReachesHow
AdministratorsNAI UI, Kommander UIBrowser to the two load-balancer addresses
Applications/enterpriseai/v1/models, /chat/completions, /completions, /embeddingsOpenAI-compatible HTTPS with Authorization: Bearer <API key>
Automation/api/enterpriseai/v1 (models, endpoints, API keys)NAI management API with an admin login

API keys. Create keys under API Client Keys and link each to the endpoints it may use; GET /enterpriseai/v1/models returns exactly those endpoints. A key that does not list an endpoint you expect is usually linked to a deleted copy of it.

When the network does not route the load-balancer addresses. In the reference lab the VPN routes only the host's own address. Users open an SSH SOCKS tunnel to the host (ssh -D 11080 user@<host-ip>) and point the browser or client at socks5://127.0.0.1:11080. On Windows, ports 1024–1123 may be reserved by Hyper-V, so choose a tunnel port outside that range. In production, route the pool addresses or publish the gateway behind a corporate load balancer instead.

Certificates on clients. Until the gateway has a CA-signed certificate, clients must either trust the self-signed one or disable verification (for example verify=False in Python). Disable verification only in test environments.

10Operations

Most day-2 issues in the reference deployment came from heat, changes that a later Helm upgrade undoes, and the self-signed certificate. Plan for each.

AreaWhat to expectWhat to do
GPU thermalsTwo workstation GPUs side by side in one chassis overheat under sustained load. A blower fan forced to 100% on one card starved the card next to it: the A6000 idled at 92 °C and throttled until the W7900 fan went back to automatic.Watch GPU temperatures (nvidia-smi, amd-smi metric --temperature). Keep fans on automatic unless one card alone is under load. Prefer data-centre GPUs with passive cooling for production.
Helm upgradeshelm upgrade nai-core re-renders NAI's deployments and drops hand-made changes such as an extra trusted certificate in nai-api.Keep every change as a Helm value or a script, and re-apply after upgrades. Use --reuse-values.
Moded-stack patchesThe AMD patches (patched nai-api and UI images, AMD runtimes in NAI's catalog, the GPU-resource webhook) are lab changes, not validated by Nutanix.Re-run the installer's AMD steps after any NAI upgrade. Do not use the Moded stack where Nutanix support is required.
Gateway certificateRenewed by cert-manager every 90 days as a new self-signed certificate.Replace it with a CA-signed certificate, or refresh every copy you trust after each renewal.
Platform dataNAI's PostgreSQL, ClickHouse and Valkey live on local volumes on one disk.Back up the data disk, or the nai-local volumes, regularly. Models can be re-imported from their source.
Kubernetes control planeSingle node: the control plane carries workloads (its taint is removed), with up to 250 pods.Accept no high availability, or move to a three-node NKP cluster.
Disk spaceEngine images land on the boot disk; models on the data disk.Alert at 80% on both. Running the boot disk full evicts pods cluster-wide.

Licences. Apply the NKP licence in Kommander (Settings → Licensing) and the NAI licence in the NAI UI after its first login. Kommander hides custom catalog applications, such as the AMD GPU Operator, until NKP is licensed.

Removing the deployment. sudo ./nai-on-nkp.sh --uninstall reverses every change the installer recorded and returns the host to its original OS. Model storage is deleted only if you confirm it separately.
