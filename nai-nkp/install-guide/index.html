Installation Guide

Nutanix Enterprise AI on Nutanix Kubernetes Platform

One script, nai-on-nkp.sh, installs a single-node NKP 2.18 cluster and Nutanix Enterprise AI 2.8.1 on an Ubuntu server in 2 to 4 hours. This guide walks through it from an empty host to a model answering API calls; planning decisions are in the companion Deployment Guide.

1Before you start

Have every item below ready; the installer asks all its questions up front and then runs unattended.

Hardware and OS

  • x86-64 server with Ubuntu 22.04, 24.04 or 26.04 installed (tested: 26.04.1, kernel 7.0), reachable over SSH
  • At least 32 CPU threads and 128 GB RAM (reference: 192 threads, 751 GB)
  • A large data filesystem: 600 GB free for the installation folder (900 GB for the Moded stack) plus at least 200 GB for models
  • At least 200 GB free under /var/lib for container images
  • NVIDIA GPU(s); for the Moded stack also an AMD Radeon PRO W7900-class GPU
  • IOMMU (AMD-Vi or VT-d) enabled in the BIOS if a GPU must be isolated with vfio

Network values

  • The host's IPv4 address, on the interface that clients reach
  • A range of at least 2 free addresses on the same subnet for MetalLB (reference: 5)
  • Internet access from the host to the Ubuntu archive, Docker Hub, GitHub and rocm.github.io during installation
  • Port 5000 free on the host (local registry)

Software and access

  • Download links or local copies of the three bundles from the Nutanix portal: NKP air-gapped bundle 2.18.0, NAI 2.8.1 image bundle, NAI 2.8.1 Helm charts. Portal links expire after about an hour, so download first if your connection is slow.
  • A non-root user with sudo on the host (the installer makes its sudo passwordless)
  • The installer nai-on-nkp.sh
  • NKP and NAI licences, applied after installation
  • A Hugging Face token (and an NGC key for NVIDIA NIM models) if you will import catalog models

2Prepare the host

Start from a clean Ubuntu install with SSH enabled; the installer adds everything else.

  1. Install Ubuntu Server and openssh-server. Create a non-root user with sudo rights, for example nutanix.
  2. Mount the large data disk, for example at /shared_storage. The installer proposes folders on the largest filesystem by default.
  3. If the host has a GPU that must not serve models (for example a small display card), enable IOMMU in the BIOS so the installer can bind it to vfio-pci.
  4. Leave the NVIDIA driver out: the installer installs the newest open driver Ubuntu offers, or keeps a working one that is already installed.
  5. Copy the installer to the host and make it executable:
scp nai-on-nkp.sh nutanix@<host-ip>:~
ssh nutanix@<host-ip>
chmod +x nai-on-nkp.sh
  1. Optional, read-only checks before installing:
sudo ./nai-on-nkp.sh --check   # host, CPU, memory, disks and GPU report
sudo ./nai-on-nkp.sh --help    # all options

4Follow progress

The whole run takes 2 to 4 hours, most of it in four stages. Watch the log from any SSH session:

sudo ./nai-on-nkp.sh --status              # answers, finished stages, recorded changes, nodes

Reboots. Before any reboot the installer enables nai-nkp-resume.service, which continues from the first unfinished stage after the host is back; follow it with journalctl -fu nai-nkp-resume. Without reboot consent it stops and asks you to reboot and re-run.

Failures. A failed stage prints the reason, failing pods and recent warning events. Fix the cause and run sudo ./nai-on-nkp.sh again: finished stages are skipped. Network downloads are retried automatically.

5Verify and log in

The installer ends with a "ready" banner listing both URLs. Confirm the cluster from the host, then log in to both UIs.

Check the cluster

export KUBECONFIG=~/.kube/config            # also <installation folder>/work/cluster/<cluster>.conf
kubectl get nodes                            # one node, Ready
kubectl get node -o jsonpath='{.items[0].status.allocatable}'   # nvidia.com/gpu: 1 (and amd.com/gpu: 1 on Moded)
kubectl -n nai-system get pods               # all Running or Completed
kubectl -n envoy-gateway-system get svc      # NAI gateway EXTERNAL-IP = second MetalLB address

Kommander (NKP)

  1. Get the login: sudo nkp get dashboard --kubeconfig ~/.kube/config.
  2. Open https://<kommander-ip>/dkp/kommander/dashboard and accept the self-signed certificate.
  3. Apply the NKP licence under Settings → Licensing. On the Moded stack, the AMD GPU Operator app appears only after this.

NAI

  1. Read the initial admin password:
kubectl -n nai-system get secret nai-default-user -o jsonpath='{.data.password}' | base64 -d; echo
  1. Open https://<nai-ip>/nai, log in as admin, and set a new password when asked.
  2. Apply the NAI licence when the UI asks for it.
  3. Under Infrastructure, check that every GPU is listed with its product name (for example NVIDIA-RTX-A6000 and AMD_Radeon_Pro_W7900).

6Serve a first model

Import one small catalog model, then create an endpoint for it; Llama-3.2-1B-Instruct is ready in about 2 minutes on either GPU.

Import the model (UI)

  1. Add your Hugging Face token once: Providers → Add Credential → platform Hugging Face.
  2. Models → Import → NAI catalog → meta-llama/Llama-3.2-1B-Instruct (about 10 GB) → select the credential → Import.
  3. Wait for status Active. NAI copies the model into its own volume on nai-nfs-storage.

To import a model that is already on the host instead, copy it to <model folder>/import/<name> and choose source NFS, server <host-ip>, share <model folder>, path import/<name>. For a custom model, tick only the capabilities it has (text-to-text, plus tool calling if supported); extra capabilities can make NAI start the wrong engine.

Create an endpoint (UI)

Local Endpoints → Create, then:

The same through the API

Useful for automation; use the admin login, for example from a .netrc file kept with mode 600.

cat > endpoint.json <<'EOF'
{"name": "llama-3-2-1b-amd", "modelId": "<model id from Models>",
 "purpose": "real-time", "platform": "amd-gpu-passthrough",
 "acceleratorProduct": "AMD_Radeon_Pro_W7900", "acceleratorCount": 1, "nodeCount": 1,
 "cpu": 8, "memoryInGi": 24, "minInstances": 1, "maxInstances": 1,
 "engine": "vllm", "engineSource": "nai"}
EOF
curl -k --netrc-file ~/.nai-netrc -H 'Content-Type: application/json' \
  -X POST -d @endpoint.json https://<nai-ip>/api/enterpriseai/v1/endpoints

For NVIDIA use "platform": "nvidia-gpu-passthrough" and "acceleratorProduct": "NVIDIA-RTX-A6000". After deleting an endpoint, wait about a minute before creating one with the same name; an immediate retry can be refused with a misleading "Provide a valid registry URL".

7Call the endpoint

Create an API key linked to the endpoint, then call NAI exactly like the OpenAI API.

  1. API Client Keys → Create → name it and select the endpoints it may use → copy the key (shown once).
  2. Check what the key can see:
curl -sk https://<nai-ip>/enterpriseai/v1/models -H "Authorization: Bearer $NAI_API_KEY"
  1. Send a chat request; the model name is the endpoint name:
curl -sk https://<nai-ip>/enterpriseai/v1/chat/completions \
  -H "Authorization: Bearer $NAI_API_KEY" -H 'Content-Type: application/json' \
  -d '{"model": "llama-3-2-1b", "messages": [{"role": "user", "content": "In two sentences, what is Nutanix?"}], "max_tokens": 200}'
  1. From Python, with the standard OpenAI client (pip install openai httpx[socks]):
import httpx, os
from openai import OpenAI

ai = OpenAI(base_url="https://<nai-ip>/enterpriseai/v1", api_key=os.environ["NAI_API_KEY"],
            http_client=httpx.Client(verify=False,                 # self-signed gateway certificate
                                     proxy=os.environ.get("NAI_PROXY")))  # e.g. socks5://127.0.0.1:11080
for chunk in ai.chat.completions.create(model="llama-3-2-1b", stream=True,
        messages=[{"role": "user", "content": "In two sentences, what is Nutanix?"}]):
    if chunk.choices:
        print(chunk.choices[0].delta.content or "", end="", flush=True)

From a laptop that cannot route to the MetalLB addresses

For example a VPN that routes only the host: open an SSH SOCKS tunnel through the host and send requests through it.

ssh -N -D 127.0.0.1:11080 nutanix@<host-ip>      # keep it open
export NAI_PROXY=socks5://127.0.0.1:11080
curl -sk --socks5-hostname 127.0.0.1:11080 https://<nai-ip>/enterpriseai/v1/models -H "Authorization: Bearer $NAI_API_KEY"

For a browser, start Chrome with its own profile and --proxy-server=socks5://127.0.0.1:11080. On Windows, avoid ports 1024–1123 if Hyper-V has reserved them (netsh int ipv4 show excludedportrange protocol=tcp).

If /models does not list an endpoint you expect, the key is not linked to it: API Client Keys → the key → Update → add the endpoint. Re-link keys after re-creating an endpoint.

8Optional features

Two features need extra configuration after installation: NAI Labs Chat and Talk to My Data, and a Remote NAI provider in the Agentic Gateway.

NAI Labs (Chat, Talk to My Data)

Agent is already on; turn on the other two with one Helm value, keeping all other settings:

KC=<installation folder>/work/cluster/<cluster>.conf
sudo helm --kubeconfig $KC -n nai-system upgrade nai-core <installation folder>/charts/nai-core \
  --reuse-values --set naiLabs.enabled=true --wait --timeout 10m
kubectl -n nai-system get pods | grep nai-labs        # Running

The UI shows NAI Labs → Chat, Talk to My Data and Agent after a refresh. Chat needs an LLM endpoint that answers within 5 seconds; Talk to My Data also needs an embedding endpoint. Undo with helm -n nai-system rollback nai-core <previous revision>.

Remote NAI provider

The form accepts only a DNS name and verifies the certificate, so the gateway's name must resolve inside the cluster and its certificate must be trusted by nai-api. With a real DNS record and a CA-signed certificate, skip to item 3. For the self-signed lab certificate:

  1. Add the gateway name to the cluster DNS (back up first):
KC=<installation folder>/work/cluster/<cluster>.conf
sudo kubectl --kubeconfig $KC -n kube-system get cm coredns -o yaml > coredns-cm.before.yaml
sudo kubectl --kubeconfig $KC -n kube-system get cm coredns -o jsonpath='{.data.Corefile}' \
 | sed 's|^    forward \. /etc/resolv.conf {|    hosts {\n       <nai-ip> nai.<cluster>.lab\n       fallthrough\n    }\n&|' > /tmp/Corefile
sudo kubectl --kubeconfig $KC -n kube-system create cm coredns --from-file=Corefile=/tmp/Corefile \
  --dry-run=client -o yaml | sudo kubectl --kubeconfig $KC -n kube-system apply -f -
  1. Make nai-api trust the gateway certificate in addition to its normal trust store:
sudo kubectl --kubeconfig $KC -n nai-system get secret ingress-certificate \
  -o jsonpath='{.data.tls\.crt}' | base64 -d > /tmp/nai-gateway.pem
sudo kubectl --kubeconfig $KC -n nai-system create configmap nai-extra-ca --from-file=nai-gateway.pem=/tmp/nai-gateway.pem
sudo kubectl --kubeconfig $KC -n nai-system patch deploy nai-api -p '{"spec":{"template":{"spec":{
  "volumes":[{"name":"nai-extra-ca","configMap":{"name":"nai-extra-ca"}}],
  "containers":[{"name":"nai-api",
    "env":[{"name":"SSL_CERT_DIR","value":"/etc/ssl/certs:/etc/nai-extra-ca"}],
    "volumeMounts":[{"name":"nai-extra-ca","mountPath":"/etc/nai-extra-ca","readOnly":true}]}]}}}}'
sudo kubectl --kubeconfig $KC -n nai-system rollout status deploy/nai-api
  1. In NAI: Providers → Add Credential → Remote Nutanix Enterprise AI. Hostname nai.<cluster>.lab (no https://, no IP), port 443, an API key from that NAI → Validate Credential → Add Credential.

CoreDNS picks up the change within about a minute. A Helm upgrade of nai-core removes the nai-api patch, and the self-signed certificate is renewed every 90 days; repeat item 2 after either.

9Troubleshooting

Every row below was met on the reference deployment. Most installation failures are network hiccups: re-run the installer and it resumes at the failed stage.

SymptomCauseFix
A stage fails pulling an image or chart (DNS errors, "awaiting headers" timeouts)Short internet outagesRe-run sudo ./nai-on-nkp.sh; downloads and mirroring retry and skip finished work
Bundle link rejected as expiredNutanix portal links last about an hourFetch a fresh link, or download the file and give its path
Cluster creation times out waiting for Cluster APIThe self-managed move did not finishRe-run; the installer detects the missing cluster object and completes the move
Kommander install hangsToo few pods allowed on a single nodeHandled: the installer sets kubelet maxPods: 250
Grafana dashboards show "No data"Datasource sidecar reload rejected (401)Handled once by the installer; repeat its reload if Grafana is re-installed

Pods evicted across the clusterBoot disk full (DiskPressure), usually from large engine imagesFree space under /var/lib; never pull large images into the host's default podman store

10Uninstall and rollback

The installer records every change it makes, so one command returns the host to its original Ubuntu install. Preview it first:

sudo ./nai-on-nkp.sh --plan         # read-only: what would be removed and what kept
sudo ./nai-on-nkp.sh --uninstall    # type 'wipe' to confirm
RemovedKept
The NKP cluster: kubeadm, kubelet, containerd, etcd, CNI, Kubernetes packagesModel folder, unless you type delete-models when asked
Local registry service, podman storage the installer createdPackages the operating system depends on (checked by a simulated purge)
Installation folder: bundles, registry data, local volumesFiles in your home folder
Host packages, NVIDIA driver and vfio settings the installer addedThe uninstall log /var/log/nai-nkp-uninstall.log
fstab, NFS export, sudoers, sysctl and swap changes (restored from backups)

The uninstall runs as the background service nai-nkp-uninstall and reboots at the end if you agree. --uninstall --yes skips the questions, keeps models and does not reboot. A host built by hand earlier can be brought under the uninstaller with --adopt.
