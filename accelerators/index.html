Why accelerators exist [top]

CPU vs GPU and the roofline

The parallelism and memory gaps

General-purpose CPUs rely on deep out-of-order pipelines and large L3 caches to hide latency; they excel at latency‑bound workloads but deliver limited throughput for massively parallel tensor operations. GPUs and AI ASICs shift the design point toward throughput: thousands of simple cores, minimal branch control, and a memory subsystem optimized for streaming massive data blocks. The roofline model quantifies the ceiling:

  • Peak compute (TFLOPS) = SM count × ops per SM per cycle × clock
  • Peak bandwidth (GB/s) = memory interface width × effective data rate
  • Arithmetic intensity = FLOP/byte; workloads to the right of the roofline roof are memory‑bound, those to the left compute‑bound
  • Transformer prefill is compute‑bound (high AI ≈ thousands FLOP/byte); decode is memory‑bound (low AI ≈ 5–20 FLOP/byte)

How a modern accelerator die computes [top]

SMs / CUDA cores and tensor cores

NVIDIA Ampere (GA100/GA102) and Blackwell (GB202)

Ampere GA102 (RTX A6000): 108 Stream Multiprocessors, 128 CUDA cores per SM, 4 3rd‑gen tensor cores per SM, 84 SMs active, 10752 CUDA cores total. Each tensor core performs a 256×256 BF16 matrix multiply‑accumulate per cycle; accumulation is in FP32. Peak BF16 Tensor throughput = 10752 cores × 2 ops/core/cycle × 1.8 GHz ≈ 989 TFLOPS (as quoted by NVIDIA).

Blackwell GB202 (RTX PRO 6000 Workstation): 2nd‑gen tensor cores supporting FP4, FP6, FP8, BF16; 5th‑gen tensor core evolution on SXM delivers 2.25 PF BF16 dense, 4.5 PF FP8 dense, 9 PF FP4 dense (sparse). Tensor core pipeline now supports unstructured N:M sparsity (2:4 mandatory on Ada/Ampere, optional on Blackwell) and native weight‑only FP4 quantization.

AMD RDNA 3 (Radeon PRO W7900): 96 Compute Units, 64 FP32 lanes per CU, no hardware tensor cores; AI/ML acceleration via ROCm WMMA (Wave Matrix Multiply‑Accumulate) and third‑party FlashInfer/AITER (not available on gfx1100). Peak FP16 matrix throughput ≈ 122.6 TFLOPS (vendor‑quoted), with AI‑specific kernels delivering ~1× the BF16 throughput of a comparable NVIDIA part when using ROCm‑optimized kernels.

Memory: the real constraint [top]

HBM vs GDDR and the memory wall

Bandwidth, capacity, and the roofline shift

High‑Bandwidth Memory (HBM) stacks dice through‑silicon vias to deliver extreme bandwidth near the GPU die. GDDR6/6E/7 sits on the PCB and is cost‑effective for workstation cards. The memory wall — compute grows ~3× per generation while memory bandwidth grows ~1.5× — means serving throughput is often limited by how fast weights and KV cache can be streamed, not by peak TFLOPS.

What inference actually demands [top]

Prefill vs decode in detail

Two phases, two bounds

Large‑language‑model serving splits naturally into a prefill phase (process the entire prompt token‑parallel) and a decode phase (generate one token at a time, repeatedly reading weights and KV cache).

Prefill

  • FLOP per output token ≈ 2 × params (BF16). For a 70‑B model: ∼140 GFLOP/token.
  • Arithmetic intensity: ∼1000–3000 FLOP/byte (compute‑bound per roofline).
  • Throughput limited by Tensor‑core MFU (typically 50–70 % of peak on H100/H200).
  • Example: H100 BF16 peak 989 TFLOPS × 55 % MFU ≈ 544 TFLOPS; 544 TFLOPS ÷ 140 GFLOP/token ≈ 3885 tokens/s theoretical peak.

Decode

  • Each output token reads the entire weight matrix once (FP16: ∼2 bytes/parameter; FP8: ∼1 byte/parameter) plus the KV cache row(s) for the current sequence.
  • Arithmetic intensity: ∼5–20 FLOP/byte (strongly memory‑bound).
  • Throughput ≈ HBM bandwidth ÷ (weights‑GB + KV‑per‑token‑GB × batch).
  • Example: 768 GB/s ÷ 18 GiB (9 B BF16 weights) ≈ 42 tok/s theoretical single‑stream.

Where this is heading [top]

2026‑2027 technology roadmap

Near‑term and long‑term trends

  • HBM4: JEDEC standard in volume production 2025‑2026; ∼2× HBM3 density per stack (∼800 GB/s per stack vs ∼418 GB/s); enables 3×+ context lengths or 2× throughput for same VRAM budget. First shipping in NVIDIA Blackwell‑based cards and AMD MI355X‑class parts.
  • FP4/FP6 native matrix cores: NVIDIA Blackwell already supports FP4 sparsity (9 PF dense‑ish); AMD CDNA4 (MI355X) adds FP4/FP6 as native tensor‑core operations. This is the biggest near‑term shift for LLM inference: 4× more parameters fit in the same bandwidth, pushing many workloads from memory‑bound toward compute‑bound.
  • MLA / KV compression: DeepSeek‑V3/R1 adoption of Multi‑Head Latent Attention compresses KV from ∼320 KiB/token (Llama‑3‑70B FP16) to ∼18 KiB/token (FP8), ∼18× reduction. Expected mainstream frameworks (vLLM, sglang) to add MLA kernels in 2025; changes the arithmetic intensity of decode dramatically.
  • Disaggregated prefill / decode: NVIDIA “Dynamo”‑style model where a subset of GPUs handles prefill (compute‑bound, high MFU) and a separate set handles decode (memory‑bound, continuous batching). Expected framework support late 2025; reduces the memory pressure on any single GPU and pushes overall system tokens/s higher.
  • Silicon‑photonic co‑packaged optics (CPO): 2025‑2026 sampling; reduces per‑link power by 5‑10× compared to electrical NVLink/Ethernet; enables 1.6 Tbps optical links between racks; scale‑out bandwidth no longer bottleneined by copper/electrical constraints. Expected in high‑end NVL72‑class systems 2026‑2027.
  • CXL 3.1 / 3.2 memory pooling: 2026 horizon; coherent memory pooling across servers using CXL 3.1’s improved switching and 3.2’s fine‑grained ownership semantics; enables very large context (1M+ tokens) without requiring every GPU to hold the full KV cache in local HBM. Early adopters: Google Cloud AXLearn, some NVIDIA proprietary stacks.
  • ASIC specialization: Groq for deterministic‑low‑latency serving; Cerebras for massive‑context on-wafer; SambaNova for full‑stack model library; AWS Trainium 3 (expected 2025) and Google TPU “Ironwood” (late 2025) will push inference‑efficiency ratios further.
  • Projected trajectory (2024‑2027): tokens/$ × 3‑5× every 2 years (historical GPU‑era trend, but memory‑wall‑limited after 2025 without HBM4/FP4); tokens/W × 2× every 2 years; the dominant bottleneck shifts from compute → memory bandwidth → KV‑cache size → interconnect, in that order, as each is solved.
