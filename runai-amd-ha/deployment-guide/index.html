Highly Available Run:ai with NVIDIA and AMD GPUs

How to plan an open-source NVIDIA Run:ai 3.0 cluster across five nodes, three control-plane nodes and one GPU server per vendor, so that losing any control-plane node interrupts users for about a minute and needs nobody to act: what runs in copies, what made failover fast enough, sizing and limits. Measured on a real lab build.

Author Manmohan Brahma Run:ai 3.0.20, open source Nodes 3 control plane + 2 GPU GPUs RTX A6000 + Radeon PRO W7900 Installation Guide oif on GitHub All guides
Lab build. Open-source Run:ai is community software without NVIDIA support, and it documents NVIDIA GPUs. The AMD GPU is scheduled through the standard Kubernetes device plugin; the limits observed are listed in this guide. Both GPUs are workstation cards. The lab runs the five nodes as virtual machines on one server, so it proves the software, not the hardware's redundancy.

1What this guide covers

This guide takes the Run:ai with NVIDIA and AMD GPUs deployment from one server to a cluster of five nodes: three control-plane nodes that run Kubernetes and the platform, and one GPU server per vendor. Any one control-plane node can lose power and users keep working: the Run:ai UI, logins and the API, new workloads in both GPU pools, quotas and the Grafana dashboards come back within 90 seconds, with nobody acting.

It is the planning half of a pair. The companion Installation Guide has the commands, the power-off demonstration and its measured results.

It is a step of a larger project: one open-source platform that schedules, serves, benchmarks and observes LLMs on NVIDIA and AMD GPUs, so the two can be compared on equal terms.

What changes from the single server:

  • One cluster, one command. oif install on the first control-plane node prepares every node over SSH (packages, kernel, containerd, the NVIDIA driver or the AMD firmware), builds the cluster with kubeadm, joins the other nodes and installs the platform. oif uninstall there removes it from every node.
  • Per-vendor node pools. GPU nodes are labelled by vendor and Run:ai gets one node pool per vendor (nvidia, amd). A project's quota is set per pool, so per-vendor quotas are Run:ai's own and the Kubernetes ResourceQuota of the single-server design is no longer needed.
  • The platform runs on the control-plane nodes, in copies on different nodes, so the GPU servers carry only GPU work.

3How the platform survives a node

High availability here means copies, not moving things after a failure. Everything users rely on runs at least twice, on different control-plane nodes, so when a node stops the other copies are already serving.

Measured on the reference lab, with the node holding both the database primary and the ingress address powered off, from a machine outside the cluster: the Run:ai UI never failed, a Run:ai login with an API call failed for 67 seconds, Grafana for 47 seconds. New workloads in both GPU pools and the quotas worked while the node was off, and every copy was complete again once it was back.

The parts that stay single (Run:ai's operators, kube-state-metrics, the Prometheus and MetalLB controllers) do not serve users directly. The ones whose loss users would notice, such as kube-state-metrics, which feeds the GPU panels, restart on another node about a minute after the node is declared down.

What makes it fast

Copies alone were not enough. Each of the following came out of a real power-off that failed:

SettingWhy
A silent node is declared down after 20 s (Kubernetes' default is 40 s)the database promotes a standby only after this verdict
max_connections 400 in PostgreSQLtwo copies of every Run:ai service filled the default 100, and Grafana was left without a connection after a failover
A connection reaper on every nodea client connected to the old database primary keeps retransmitting for about 15 minutes. Keycloak and Run:ai's services hung on the dead primary, and logins failed while every pod looked healthy. A small host service drops connections whose destination no longer exists, and the clients reconnect at once
The ingress address only on control-plane nodesKubernetes marks control-plane nodes as excluded from load balancers, so MetalLB had announced the address from a GPU server
20 s moves for the single services users misswith the default 5 minutes the GPU panels were empty for about 8 minutes
wal_keep_size 4 GBa database copy whose node was off for hours must catch up from the primary's log; the default 512 MB lasted about 2.5 hours in the lab

Storage

Components that copy their own data (PostgreSQL, Thanos receive, Prometheus) keep it on local disks through local-path, one volume per copy. Longhorn holds only what has no copies of its own (NATS). Replicating already-replicated data through Longhorn as well would have needed about 300 GB per node.

5Reference hardware and sizing

The reference is the Hybrid GPU Cluster Lab: five virtual machines on one server, each GPU passed through to its VM.

NodevCPUMemoryDiskGPU
cp1, cp2, cp32448 GB500 GBnone
gpu-amd4896 GB500 GBRadeon PRO W7900, 48 GB
gpu-nvidia4896 GB500 GBRTX A6000, 48 GB

With the platform in copies, a control-plane node uses about 4 to 10 GB of memory. Each one must be able to carry its share of the copies of a node that is down; 16 GB is the practical floor and 32 GB is comfortable. Plan disk for the database (20 GB volume per copy) and Prometheus on every control-plane node.

Three is the minimum: etcd and the database need a majority, so a cluster of three survives one lost node. A cluster with fewer than three control-plane nodes keeps the single-server design (single copies, Run:ai's built-in database).

6Design decisions

DecisionWhy
Copies on different nodes, not volumes that movemoving a volume and restarting a service after a node failure took about 14 minutes in the first test; copies take seconds
An external, replicated database (CloudNativePG)Run:ai's built-in PostgreSQL cannot be replicated; Run:ai documents an external database for high availability
One node pool per vendorquotas per pool are per-vendor quotas, set in Run:ai's UI, with no Kubernetes objects of our own
The platform on the control-plane nodesGPU servers carry only GPU work and can be added or removed without touching the platform
Measured from outside the clusterinside the cluster kube-proxy answers the ingress address itself, so an inside probe cannot see the address move. The acceptance test probes a real login from a machine outside
No automatic fencing yetcopies already avoid the outage; fencing would only restore full redundancy sooner

7Known issues and limits

  • A database copy whose node stays off for longer than about 20 hours (at the lab's write rate) cannot catch up when it returns. Rebuild it: delete its volume and pod, and CloudNativePG clones it from the primary in about a minute.
  • A network interruption to a node longer than 20 s counts as a node failure: the database fails over and the singles move.
  • Run:ai's operators keep Kubernetes' 5-minute eviction (Run:ai's own operator owns their settings). They do not serve users; changes to Run:ai's configuration wait for them while their node is down.
  • Every other limit of the single-server deployment still applies, including GPU fractions staying off while the NVIDIA driver is older than r615.

9Checklists

Before installing

  • Three control-plane machines and at least one GPU server per vendor, on one subnet, Ubuntu 26.04, one user with SSH keys and sudo without a password
  • A free address for the Kubernetes API and a small range for MetalLB on that subnet
  • Each GPU server holds GPUs of one vendor
  • A machine outside the cluster that reaches the ingress address, to measure what users see

After a node failure

  • Logins and the Run:ai API work within 90 seconds
  • The database has a primary on a live node; three ready instances once the node is back
  • The GPU panels in Grafana show both vendors
